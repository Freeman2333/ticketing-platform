# Step 7 Implementation Plan — Organizer Dashboard (Phase 6)

## Status

In progress. `project-plan.md` §5 lists this under Phase 6 ("Microfrontend expansion... admin dashboard"), originally scheduled after Phase 5 (Kafka + analytics) — reordered ahead of it by explicit choice (2026-10-26), since Phase 5 isn't designed yet and this phase has a concrete, already-partially-built priority (event/venue/seat management).

Part A (scope) decided. Part B (MFE scaffold + role gating) done. Part C (backend gap) done. Part D: all venue pages done (list, create, details+stats, edit); event pages not started.

## Part A — Scope

- [x] This is an **organizer self-service portal**, not a platform-wide admin panel. `project-plan.md`'s "admin dashboard" wording is imprecise — the actual priority (create event, add venues/seats, set prices) maps to the existing `Role.organizer` and its ownership-scoped endpoints (`venue.organizerId === req.user.sub`), not `Role.admin`, which exists in the schema but is unused by any endpoint. A true platform-wide admin view, if ever built, is a separate future piece.
- [x] Pages for this first version:

  | Route | Purpose |
  |---|---|
  | `/organizer` | List of the organizer's own events — a compact row list (small thumbnail + title, etc.), not the showcase-style `EventCard` the public catalog uses for attendees picking an event |
  | `/organizer/venues` | List of the organizer's own venues (as links) |
  | `/organizer/venues/new` | Create venue form — a separate page from the list, not combined on one screen |
  | `/organizer/venues/:id` | Venue details (incl. image) + the list of its own events |
  | `/organizer/events/new` | Create event (pick an existing venue) |
  | `/organizer/events/:id` | Event details + basic stats + seat/price management |
  | `/organizer/events/:id/edit` | Edit event |

- [x] Stats on the event details page are computed from data already returned by the existing, public `GET /events/:id/seats` (each seat has `status` and `price`) — no new backend aggregation needed for this first version. A richer, cross-event CQRS read-model (discussed separately) is a later, independent enhancement, not a prerequisite.
- [x] Deferred, not scoped in this step: CQRS read-model for dashboard stats, a GraphQL/BFF layer (only worth it if this grows into a full multi-entity admin panel), Elasticsearch (only if search/filtering at scale is needed), an AI-agent/copilot (natural-language queries over organizer data, likely as its own `/organizer/assistant` page later, feeding off the CQRS aggregates once those exist).

## Part B — MFE scaffold + role gating

Verified standalone on port 4202 before wiring into `shell`.

- [x] `useUserRole()` added to `@ticketing/auth-client` — decodes the `role` claim already present in the JWT access token (no extra API call). `Header.tsx` shows the "Organizer" nav link only for `role === 'organizer'`. A new `RequireRole` wrapper in `shell` redirects to `/` for any other role when navigating to `/organizer` directly. This is a UX gate only — real enforcement stays server-side via `RolesGuard`.

## Part C — Backend gap

- [x] `GET /events` is public with no organizer filter. Added `GET /events/mine` (`@Roles(Role.organizer)`), mirroring `VenuesController.findMine()` (`venuesRepository.findByOrganizerId(req.user.sub)`). Implemented and committed; manual end-to-end verification (real browser flow) deferred.
- [x] `Venue` has no image field (`name`/`address` only, unlike `Event.posterUrl`). Added `imageUrl String?` + migration, and `POST /venues/:id/image` mirroring `events.controller.ts`'s `uploadPoster` — reuses the already-generic `PosterStorageService.upload(key, buffer, contentType)` and `processPosterImage` (sharp resize to webp), just a different S3 key prefix (`venues/${id}.webp` vs `events/${id}.webp`). Implemented and committed.
- [x] Venue-level stats (tickets sold / revenue across all of a venue's events) — decided 2026-10-27: a venue's stats are an aggregate across multiple events, unlike a single event's stats (one `GET /events/:id/seats` call). Computing this by fetching every event's seats client-side would be N+1. Added `GET /venues/:id/stats`, one Prisma aggregate query (`SeatsRepository.aggregateByVenueId` — `seat.aggregate` filtered through `event.venueId`, `status: 'booked'`) — not CQRS, deferred as a dedicated future exercise. **Superseded 2026-10-29 by Part E** — the CQRS exercise is happening now, not later, but for a different reason than originally planned (see Part E): removing `Seat.price` (to stop duplicating `OrderItem.price`) forced the revenue half of this query off `Seat` entirely, and a cross-module read turned out to need a projector anyway to avoid a circular module dependency. `ticketsSold` still comes straight from `Seat` (a plain count, no price involved); only `revenue` moves to the Part E read-model.

## Part D — Pages

- [x] `/organizer/venues` — list (`GET /venues`, already organizer-scoped), each row a `VenueListItem` component linking to `/organizer/venues/:id`. Empty state links to the create page, doesn't inline the form. Implemented and committed.
- [x] `/organizer/venues/new` — single form (name, address, image dropzone together — not split into two steps), submits `POST /venues` then `POST /venues/:id/image` sequentially under one "Create" action. Image picker uses `react-dropzone` (not hand-rolled — avoids the drag-leave-on-child-element flicker and missing drop-time type filtering a custom version had). Implemented and committed.
- [x] `/organizer/venues/:id` — venue details (image/placeholder, name, address) + stats cards (tickets sold, revenue) + its events, paginated with a "Load more" button (`useMyEvents` hook shared with `OrganizerEventsPage`, filtered server-side via `GET /events/mine?venueId=` — switched from a client-side `select` filter once `/events/mine` itself became paginated, since filtering only the loaded page would silently hide events on later pages). One Suspense boundary coordinates venue + stats + events. "Edit" and "Delete" buttons gated client-side too (`venue.organizerId === useUserId()`) as well as server-side — redundant given the server check, but added since explicitly requested. Delete uses the existing `ConfirmDialog` component and `DELETE /venues/:id`, which 409s if the venue still has events (`useDeleteVenue` hook, `organizer/src/venues/hooks/`); success/failure reported via `sonner` toast (`sonner` added as an MF shared singleton across shell/catalog/organizer so `toast()` from any remote reaches the one `<Toaster/>` in `shell`). Implemented and committed.
- [x] `/organizer/venues/:id/edit` — form prefilled from `GET /venues/:id` (name, address, current photo as the dropzone's initial preview via `ImageDropzone`'s new `initialImageUrl` prop). Deliberately **not** a form shared with `CreateVenuePage` — different Zod schema (update fields optional vs create required), different submit sequence, different default values, different post-save destination (back to the venue, not the list); considered and rejected sharing even just the two `FormField`s, same "don't abstract two text fields" reasoning. Submit: `PATCH /venues/:id`, then `POST /venues/:id/image` only if a new file was picked, then invalidates both `findMine` (list) and this venue's `findOne` cache — a real case of the broader-than-single-key invalidation discussed earlier (an edit affects both the list and the detail view, unlike a create which only affects the list). Implemented and committed.
- [x] `/organizer` — events list (`OrganizerEventsPage`, same Suspense+ErrorBoundary+`EventListItem` pattern as `VenuesPage`), paginated with a "Load more" button via the shared `useMyEvents` hook (`organizer/src/hooks/useMyEvents.ts`). `GET /events/mine` outgrew a flat array once there were enough test events to notice — added real pagination (`page`/`limit` → `EventListDto`, plus an optional `venueId` filter for the venue-details use), mirroring the public `listEvents`'s exact approach. Extracted the shared offset-pagination logic (skip/take math, N+1-fetch hasMore detection) into `paginate()` (`events/internal/paginate.ts`, unit-tested) since both `listEvents` and `listMyEvents` had it duplicated. Implemented and committed.
- [ ] `/organizer/events/new` — decided 2026-10-29: **one page**, not a wizard — venue picker, title, start date, and ticket types all on the same form, one "Create" action that sequences `POST /events` then `POST /events/:id/seats` (same pattern as `CreateVenuePage`'s form+image). Ticket types use a card-per-type layout, following Eventbrite's actual ticket-creation UI (researched, not guessed): each card is one `{label, count, price}` row with a delete button in the corner, an "+ Add ticket type" button appends another card, minimum one card required. No "sections" (Eventbrite has them for per-section capacity) — out of scope, adds complexity we don't need. Not started.
- [ ] `/organizer/events/:id` — read-only details + stats (`ticketsSold` from `Seat` count, `revenue` from Part E's read-model) + a read-only list of ticket types (`GET /events/:id/seat-types`). Editing lives on the edit page, not here.
- [ ] `/organizer/events/:id/edit` — `PATCH /events/:id` (title/startsAt) **plus** ticket-type management: existing types shown as editable price cards (`PATCH /events/:id/seat-types/:seatTypeId`), and the same "+ Add ticket type" card UI as the create page to add new types to an already-existing event (`POST /events/:id/seats`, no longer blocked once seats exist — see Part E).
- [ ] AI-assisted event description generation on the create form — explicitly scoped **out** of this pass, to be added later as its own separate piece (not during initial CRUD build).

## Part E — Seat types and the revenue read-model

Decided 2026-10-29, while designing the event create/edit pages:

- [ ] **Schema**: new `SeatType { id, eventId, label, price }` (`@@unique([eventId, label])`). `Seat` gains `seatTypeId` (FK) and **loses `price`** — `OrderItem.price` (in the `orders` schema) already snapshots what was actually charged per seat at order-creation time, so keeping a price on `Seat` too was a genuine third copy of the same number (`SeatType.price` = current/template, `Seat.price` would've been a redundant middle copy, `OrderItem.price` = the real historical record). `Seat.label` stays (it's not a duplicate of `SeatType.label` — "VIP1" vs "VIP", generated from it, not equal to it).
- [ ] **`POST /events/:id/seats`** behavior change: no longer rejects a second call once the event has seats. Each row in the body creates one new `SeatType` + its seats; 409 only if a type with that label already exists for this event (`@@unique` constraint). Used both by the create-event page (one call, several rows) and the edit page's "add ticket type" (a later call, more rows). Response becomes `SeatTypeDto[]` (was `SeatDto[]`).
- [ ] **`GET /events/:id/seat-types`** (new, organizer-only) — `SeatTypeDto[]` with per-type counts (`availableCount`/`heldCount`/`bookedCount`), computed by including each type's seats and reducing by status in application code (counts are small and bounded per event — no SQL `groupBy` needed, same "don't over-engineer the small case" reasoning used elsewhere).
- [ ] **`PATCH /events/:id/seat-types/:seatTypeId`** (new) — body `{ price }`. Updates `SeatType.price`, then bulk-updates `price` on that type's `available` seats only. `held` and `booked` seats keep whatever price they already had — a sale in progress or already completed must not change price under the buyer. Also validates `seatType.eventId` matches the `:id` in the URL (not just that the event belongs to the organizer) — otherwise an organizer could accidentally target a seat type from a *different* one of their own events.
- [ ] **Revenue read-model, not a direct cross-module call**: computing venue/event revenue from `OrderItem.price` would mean the `events` module reading `orders` module data. The obvious NestJS way (`events` imports `OrdersModule` for its `ORDERS_API` token, mirroring how `orders`/`auth` already consume `EVENTS_API`) was rejected: `OrdersModule` already imports `EventsModule`, so the reverse import closes a cycle (`EventsModule → OrdersModule → EventsModule`), fixable only with `forwardRef()` — and `forwardRef` only works because both modules share one process/DI container today. Given `notifications` has already been extracted into a genuinely separate process (`extraction-design.md`) and `project-plan.md` names microservices as an explicit priority, that assumption is exactly the one most likely to stop holding later — `forwardRef` would have to be unwound the moment `orders` or `events` is extracted, while a RabbitMQ consumer doesn't care whether the publisher is in the same process or across the network. So: `events` gets its own small consumer that reacts to the *existing* `order.paid`/`order.issued` outbox messages (today's payload only carries `seatLabel`, not `seatId`/`price` per item — needs enriching) and maintains its own local revenue number per event, incrementally, as those messages arrive. `aggregateByVenueId` keeps counting `ticketsSold` straight from `Seat` (unaffected by any of this) but sources `revenue` from this new read-model instead of `_sum: { price }`. Accepted trade-off: revenue is eventually consistent (a short lag after payment, not instant), same as the rest of the order/payment pipeline already is. This *is* the CQRS exercise Part C deferred — it ended up happening for a coupling reason, not a performance one, which turned out to be the more honest justification anyway.
- [ ] Still to pin down while implementing: exact shape of the new read-model table, which outbox event to consume (`order.paid` vs `order.issued`), and idempotent-consumption handling (RabbitMQ can redeliver).

## Not in this step

- Platform-wide admin role/view (`Role.admin` stays unused).
- GraphQL/BFF, Elasticsearch, AI-agent — still explicitly deferred (Part A). CQRS is no longer entirely deferred — see Part E: a RabbitMQ-fed revenue read-model is now in scope, but only because removing `Seat.price` forced revenue off `Seat` and a direct cross-module read would've created a circular module dependency (`events` ↔ `orders`) — not because a single event's or venue's seat aggregate was ever too slow to query directly. The two decisions below (2026-10-29, made *before* that discovery, while just scoping the event page) are superseded by Part E for revenue specifically, but the underlying reasoning — don't reach for CQRS just because the word sounds impressive — still applies everywhere else:
  - A single event's stats being "the same shape of problem as venue stats" (cheap aggregate, no real need for a read-model) was true and is why `ticketsSold` still comes from a plain `Seat` count in Part E, not from any projection.
  - A cross-entity organizer dashboard (totals across *all* of an organizer's events/venues) remains a plausible **later**, bigger CQRS exercise if Part E's per-event read-model ever needs rolling up further — not started now.
- A new RabbitMQ consumer for something unrelated to revenue (e.g. async seat generation for a very large venue) was considered and rejected — it only reads as justified under an invented stadium-scale assumption, not the actual data volumes in this project. (Part E's consumer is unrelated to this — it exists for the module-coupling reason above, not for scale.)
